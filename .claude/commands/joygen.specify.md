## 通用指南

## 快速指南

- 专注于用户需要**什么**和**为什么**。
- 避免如何实现（没有技术栈、API、代码结构）。
- 为业务利益相关者而不是开发人员编写。
- 不要创建嵌入在规约中的任何检查清单。那将是一个单独的命令。

### 部分要求

- **必需部分**：每个功能都必须完成
  - 产品概述（第1节）：必须包含，但可根据描述简化某些子节
  - 功能规格（第2节）：必须包含
  - 用户流程（第3节）：必须包含
  - 用户场景与测试（第6节）：必须包含
  - 需求（第7节）：必须包含
  - 成功标准（第8节）：必须包含
- **条件必需部分**：
  - 数据流设计（第4节）：如果功能涉及数据存储和处理，则必须包含
  - 页面规格（第5节）：如果是Web应用或移动应用，则必须包含
- **可选部分**：仅在与功能相关时包含
  - 功能模块间的关系图（第2.2节）
  - 关键数据流向图（第4.2节）
  - 数据存储与处理原则（第4.3节）
  - 市场需求与竞品简析（第1.6节）
- 当某个部分不适用时，完全删除它（不要留作"N/A"）

### AI生成指南

从用户提示创建此规约时：

1. **做出明智的猜测**：使用上下文、行业标准和常见模式来填补空白
2. **记录假设**：在假设部分记录合理的默认值
3. **限制澄清**：最多3个 [NEEDS CLARIFICATION] 标记 - 仅用于以下关键决策：
   - 显著影响功能范围或用户体验
   - 存在多个合理解释且具有不同含义
   - 缺乏任何合理的默认值
4. **优先级澄清**：范围 > 安全/隐私 > 用户体验 > 技术细节
5. **像测试人员一样思考**：每个模糊的需求都应该在"可测试和明确"检查清单项目中失败
6. **需要澄清的常见领域**（仅当不存在合理默认值时）：
   - 功能范围和边界（包含/排除特定用例）
   - 用户类型和权限（如果可能存在多个冲突解释）
   - 安全/合规要求（当法律/财务上重要时）

**合理默认值的示例**（不要询问这些）：

- 数据保留：该领域的行业标准实践
- 性能目标：除非指定，否则为标准web/移动应用期望
- 错误处理：用户友好的消息和适当的回退
- 认证方法：web应用的标准基于会话或OAuth2
- 集成模式：除非另有规定，否则为RESTful API

### 功能规格生成指南

生成功能规格时：

1. **功能模块划分**：
   - 按业务逻辑将功能分组（如：用户管理、核心业务、数据管理、消息通知等）
   - 每个模块使用清晰的命名

2. **功能ID规范**：
   - 格式：`F-[MODULE]_XXX`，其中MODULE是模块缩写（如USER、LOTTERY、PRIZE）
   - XXX是三位数字，从001开始
   - 示例：`F-USER_001`、`F-LOTTERY_002`

3. **优先级分配**：
   - P0：核心功能，必须实现
   - P1：重要功能，影响主要用户体验
   - P2：次要功能，可以后续迭代

4. **功能描述要求**：
   - 清晰、具体、可测试
   - 描述"做什么"，不描述"怎么做"
   - 避免技术实现细节

5. **功能关系图**：
   - 如果功能模块间有明显依赖关系，使用Mermaid流程图展示

   - 一致性：事务、锁机制等
   - 实时性：数据更新频率要求
   - 可追溯性：日志、审计等
   - 扩展性：分库分表、缓存等考虑

### 页面规格生成指南

生成页面规格时（如果是Web/移动应用）：

1. **页面识别**：
   - 从用户流程和功能规格中识别所有页面
   - 为每个页面分配唯一ID（格式：`P-[PAGE_ID]`）
   - 示例：`P-LOGIN`、`P-HOME`、`P-PROFILE`

2. **页面详情描述**：
   - **页面名称与目的**：一句话说明页面用途
   - **核心功能**：列出该页面负责的功能ID
   - **主要UI元素**：描述关键UI组件和布局建议（不涉及具体样式）
   - **关键数据**：列出页面需要展示的数据项

3. **页面组织**：
   - 按用户使用频率或业务流程顺序组织
   - 核心页面（如首页、登录页）优先描述

### 成功标准指南

成功标准必须是：

1. **可测量的**：包含具体指标（时间、百分比、计数、比率）
2. **技术无关的**：不提及框架、语言、数据库或工具
3. **以用户为中心的**：从用户/业务角度描述结果，而不是系统内部
4. **可验证的**：可以在不了解实现细节的情况下测试/验证

**好的示例**：

- "用户可以在3分钟内完成结账"
- "系统支持10,000个并发用户"
- "95%的搜索在1秒内返回结果"
- "任务完成率提高40%"

**坏的示例**（以实现为中心）：

- "API响应时间低于200毫秒"（过于技术化，使用"用户立即看到结果"）
- "数据库可以处理1000 TPS"（实现细节，使用面向用户的指标）
- "React组件高效渲染"（特定于框架）
- "Redis缓存命中率超过80%"（特定于技术）
