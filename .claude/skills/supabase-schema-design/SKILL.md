# Supabase Schema Design Skill

此技能专注于 **数据库架构设计 (Schema Design)** 和 **迁移管理 (Migration Management)**。
核心目标是生成标准化的 SQL Migration 文件，并**立即**在 Supabase 数据库中执行变更，确保代码与数据库状态同步。

## 核心职责

1.  **Schema 设计与变更**：基于业务需求设计合理的数据库表结构，支持增量变更（ALTER TABLE）。
2.  **Migration 管理**：生成符合规范的 SQL 迁移文件，确保版本控制和可追溯性。
3.  **强制执行变更**：**必须**调用 MCP 工具将变更应用到数据库，严禁只生成文件不执行。

## 工具选择策略 (CRITICAL)

在执行任何操作前，**必须**检查可用的 MCP 工具集，并按照以下优先级选择：

1.  **优先级 1: JoyTable (最高优先)**
    - **触发条件**: 只要系统提供了 `mcp__joytable__*` 系列工具。
    - **行为**: **必须**优先使用 JoyTable 工具集进行所有 Schema 操作。即使 Supabase 工具也存在，也**必须**忽略 Supabase 工具。
    - **工具前缀**: `mcp__joytable__*`

2.  **优先级 2: Supabase**
    - **触发条件**: 未提供 JoyTable 工具，但提供了 `mcp__superbase__*` 系列工具。
    - **行为**: 使用 Supabase 工具集。
    - **工具前缀**: `mcp__superbase__*`

3.  **冲突处理原则**
    - 如果两个工具集都存在，**强制选择 JoyTable**。
    - **严禁**在一个任务中混用两套工具。一旦选定 JoyTable，就只用 JoyTable 的工具（如 `mcp__joytable__list_tables`, `mcp__joytable__apply_migration`）。

## 工具能力 (MCP)

你必须熟练使用以下 Supabase 和 JoyTable MCP 工具。根据上述策略选择对应的工具集。

1.  **项目定位**
    - **JoyTable**: `mcp__joytable__list_projects` (如果可用)
    - **Supabase**: `mcp__superbase__list_projects`

2.  **Schema 变更**
    - **JoyTable**:
        - `mcp__joytable__apply_migration`: **(核心)** 执行 DDL 语句。
        - `mcp__joytable__create_database`: 创建新的数据库实例。
        - `mcp__joytable__execute_sql`: (备用) 执行原始 SQL。
    - **Supabase**:
        - `mcp__superbase__apply_migration`: **(核心)** 执行 DDL 语句。
        - `mcp__superbase__execute_sql`: (备用) 仅在 apply_migration 不适用时使用。

3.  **验证 & 查询**
    - **JoyTable**: `mcp__joytable__list_tables`, `mcp__joytable__list_migrations`
    - **Supabase**: `mcp__superbase__list_tables`, `mcp__superbase__list_migrations`

## 执行原则 (严格遵守)

1.  **环境探测与智能变更（重要）**
    - 在生成 SQL 之前，**必须**先调用 `list_tables` 检查目标表是否存在。
    - **表不存在**: 生成 `CREATE TABLE` 语句。
    - **表已存在**:
        - 对比现有结构与需求。
        - 生成 `ALTER TABLE` 语句以添加缺失列或修改列属性。
        - **严禁**直接生成 `CREATE TABLE IF NOT EXISTS` 而不处理潜在的结构差异，这会导致旧表结构不更新。
    - 确保生成的 SQL 能够安全地在现有数据上运行（考虑 DEFAULT 值等）。

2.  **强制执行策略 (CRITICAL)**
    - **生成即执行**：Migration 文件生成后，**必须立即**调用 `mcp__joytable__apply_migration` (或 `mcp__superbase__apply_migration`) 将变更应用到数据库。
    - **禁止仅生成不执行**：严禁只生成 SQL 文件就结束任务。文件只是中间产物，数据库状态的改变才是最终交付物。
    - **验证**：执行完成后，必须调用 `list_tables` 或查询元数据来验证变更已生效。

3.  **Migration 文件管理**
    - 所有变更必须先落地为 SQL 文件（`migrations/` 目录下）。
    - 文件名必须包含时间戳，确保顺序。
    - 文件写入成功后，立即读取该文件内容并作为参数传递给 `apply_migration` 工具。

4.  **安全性**
    - SQL 必须兼容 PostgreSQL。
    - 涉及破坏性操作（DROP/RENAME）必须使用 `IF EXISTS` / `IF NOT EXISTS` 等安全写法。
    - 生产环境变更需格外谨慎。

5.  **聚焦当前需求（关键）**
    - **仅**生成与当前业务需求直接相关的数据模型。
    - **禁止**生成未被引用的、推测性的或“为了完整性而补充”的额外表结构。

## Schema 设计规范

- **命名**: 表名、字段名统一使用 `snake_case`。
- **主键**: 必须显式声明主键 (Primary Key)。
- **JoyTable 模式 ID 限制**:
  - **严禁**使用自增列（AUTO INCREMENT, SERIAL）。
  - **严禁**使用 `GENERATED BY DEFAULT AS IDENTITY` 或 `GENERATED ALWAYS AS IDENTITY`。
  - 推荐使用非自增的整数或 UUID 作为主键，由应用层或后端逻辑生成 ID。
- **约束**: 外键、唯一约束、索引必须显式声明。
- **通用字段**:
  - `created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()`
  - `updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()`

## Migration 文件规范

- **目录**: `migrations/`
- **文件名**: `<yyyyMMddHHmm>_<short_description>.sql` (例如: `202310271030_create_users_table.sql`)
- **内容格式**:
  ```sql
  -- migration: <yyyyMMddHHmm>_<short_description>
  BEGIN;
    -- SQL statements here
  COMMIT;
  ```

## 工作流程

1.  **环境探测**:
    - 确定是 JoyTable 还是 Supabase 环境。
    - 调用 `list_tables` 获取当前数据库表列表。
2.  **分析与设计**:
    - 检查目标表是否在列表中。
    - **如果不存在**: 设计 `CREATE TABLE` 语句。
    - **如果存在**: 分析差异，设计 `ALTER TABLE` 语句（如 `ADD COLUMN IF NOT EXISTS`）。
3.  **生成文件**:
    - 确定文件名（使用当前时间戳）。
    - 写入 SQL 内容到 `migrations/` 目录。
4.  **执行变更 (MANDATORY)**:
    - **必须**调用 `mcp__joytable__apply_migration` (或 `mcp__superbase__apply_migration`)。
    - 将刚才生成的 SQL 语句作为参数传入。
5.  **验证反馈**:
    - 再次调用 `list_tables` 确认表结构已更新。
    - 汇报执行结果：“Migration 文件已生成并成功应用到数据库”。
